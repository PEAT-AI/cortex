## 2026-11-10 — starting point and decisions

### why now
`butterfly` runs EKS 1.34. Standard support for 1.34 ends **2026-12-02**. The cluster's upgrade policy is `EXTENDED`, so it keeps running after that date but at the extended-support price.

```
aws eks describe-cluster-versions --region ap-south-1 --profile ml-admin
1.37  STANDARD_SUPPORT  default  standard until 2027-12-01
1.36  STANDARD_SUPPORT           standard until 2027-08-02
1.35  STANDARD_SUPPORT           standard until 2027-03-27
1.34  STANDARD_SUPPORT           standard until 2026-12-02
1.33  EXTENDED_SUPPORT
```

Note for the cadence: each EKS version gets ~14 months of standard support. 1.37 covers us until 2027-12-01, so the next round has to start around October 2027, not in 18 months.

### which version
**1.37.** It is the newest on EKS (released there 2026-10-01). Kubernetes 1.38 is only a beta upstream (final planned 2026-12-16), so EKS won't have it before roughly Jan/Feb 2027; waiting would mean two months at the extended price.

AL2023 nvidia AMI for 1.37 exists in ap-south-1: `amazon-eks-node-al2023-x86_64-nvidia-1.37-v20261107`.

### current state (before any change)
- cluster `butterfly`: EKS 1.34, platform eks.37, created 2025-11-05, cortex images 0.45.0. Only cluster in ap-south-1 (no butterfly-dev / butterfly-batch).
- nodes: 4× t3.medium, 4× g4dn.xlarge (2 on-demand, 2 spot — the spot ones launched today 19:55 UTC, so T4 spot was obtainable today).
- EKS addons on it: vpc-cni, coredns, kube-proxy, metrics-server, aws-ebs-csi-driver.

- cortex repo: branch `plantix`, clean apart from untracked local files.

## 2026-11-10 — Task 7: cluster-autoscaler — STOPPED, needs a decision

- `git cherry-pick` of our three rate-limiter commits onto upstream tag `cluster-autoscaler-1.37.0` fails with modify/delete conflicts on every file: the files do not exist any more.
- reason: **with 1.37.0 upstream moved the autoscaler core out of `kubernetes/autoscaler`** into a new repo and Go module, `kubernetes-sigs/cluster-autoscaler` (`sigs.k8s.io/cluster-autoscaler`, tag `v0.0.0-k8s.v1.37.1`). `kubernetes/autoscaler/cluster-autoscaler` now only holds `main.go`, the cloud providers and the APIs. `core/`, `config/`, `provisioningrequest/` — everything our patch touches — is gone from the repo we forked.
  - 1.35.3 and 1.36.2 still have the core in the old place; 1.37.0 is the first without it.
- aborted the cherry-pick, deleted the empty local branch, `~/projects/autoscaler` is back on `cluster-autoscaler-1.34.1-cortex`, nothing pushed.
- options:
  1. **drop the rate limiter**, build upstream `cluster-autoscaler-1.37.0` unchanged, remove the three `--scale-up-*` flags from `cluster-autoscaler.yaml.j2`. The limiter caps scale-up at 50 nodes/min (burst 75); Butterfly has at most 7 worker nodes, so it can never trigger. No fork to maintain any more.
  2. **keep the limiter, fork the new repo too**: port the patch to a fork of `kubernetes-sigs/cluster-autoscaler` and point our `kubernetes/autoscaler` fork at it with a `replace` in `go.mod`. Two forks to carry from now on.
  3. **keep the limiter on 1.36.2** (last version with the old layout) and run it against k8s 1.37. One minor version behind the cluster, which upstream does not recommend.
- done already, valid for options 1 and 2:
  - upstream example manifest 1.34.1 → 1.37.0 has exactly one change: a new ClusterRole rule for `resource.k8s.io` (`deviceclasses`, `resourceslices`, `resourceclaims`: watch/list/get). Added to `manager/manifests/cluster-autoscaler.yaml.j2`; compared all rules by script, cortex and upstream are now identical. "Source:" link in the template updated to 1.37.0.
  - checked every flag of our manifest against `registry.k8s.io/autoscaling/cluster-autoscaler:v1.37.0 --help`: all exist except the three rate-limit flags.
