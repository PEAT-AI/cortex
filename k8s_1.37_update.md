## 2026-11-10 — starting point and decisions

### why now
`butterfly` runs EKS 1.34. Standard support for 1.34 ends **2026-12-02**. The cluster's upgrade policy is `EXTENDED`, so it keeps running after that date but at the extended-support price.

```
aws eks describe-cluster-versions --region ap-south-1 --profile ml-admin
1.37  STANDARD_SUPPORT  default  standard until 2027-12-01
1.36  STANDARD_SUPPORT           standard until 2027-08-02
1.35  STANDARD_SUPPORT           standard until 2027-03-27
1.34  STANDARD_SUPPORT           standard until 2026-12-02
1.33  EXTENDED_SUPPORT
```

Note for the cadence: each EKS version gets ~14 months of standard support. 1.37 covers us until 2027-12-01, so the next round has to start around October 2027, not in 18 months.

### which version
**1.37.** It is the newest on EKS (released there 2026-10-01). Kubernetes 1.38 is only a beta upstream (final planned 2026-12-16), so EKS won't have it before roughly Jan/Feb 2027; waiting would mean two months at the extended price.

AL2023 nvidia AMI for 1.37 exists in ap-south-1: `amazon-eks-node-al2023-x86_64-nvidia-1.37-v20261107`.

### current state (before any change)

## 2026-11-10 — first `cluster up` failed: credentials bug with SSO (fixed)

- the first `cortex cluster up` for butterfly-dev stopped after 54 seconds, **before anything was created** (no CloudFormation stack):
  ```
  ￮ using existing s3 bucket: butterfly-dev-e08551c1 ✓
  error: failed to get account ID: NoCredentialProviders: no valid providers in chain. Deprecated.
  ```
- cause: `pkg/lib/aws/cloudwatch.go` `getAccountID()` (called by `DoesLogGroupExist`, used in `cluster up` and `cluster down`) did not use the CLI's AWS client. It built a fresh `session.NewSession()`, which does not read `~/.aws/config`. With the old `thomas-cortex` IAM user the keys were in `~/.aws/credentials`, which a bare session does read, so it worked. An SSO profile like `ml-admin` lives only in `~/.aws/config` → no credentials. So this is a leftover from the SSO switch (Butterfly#97), not from the Kubernetes upgrade. Everything else in the CLI creates its sessions with `SharedConfigEnable` and was fine.
- fix: `getAccountID()` now calls `c.STS().GetCallerIdentity(...)`, i.e. the client's own session.

## Next time

**Deadline: EKS 1.37 leaves standard support on 2027-12-01. Start by October 2027.** This round took two working days (2026-11-10 and 11) plus the parallel days.

What to do differently, or not to forget:

- **Pick the version** with `aws eks describe-cluster-versions`; it also shows the end of standard support for each version.
- **kube-proxy:** if the target is 1.40 or later, `setup_ipvs` has to move to nftables first. 1.37 already logs the deprecation.
- **Cluster autoscaler:** we run the upstream image now. Compare our flags with `--help` of the new version, and keep `AWS_REGION` in the manifest.
- **Go modules:** try the "bump in place" path in `dev/versions.md` first. It worked without source changes for 1.34 → 1.37.
- **Whitelist CIDRs must be canonical** (`15.177.50.0/24`, not `15.177.50.88/24`). The CLI now refuses others before `cluster up` starts.
- **SSO:** run `aws sso login --profile ml-admin --use-device-code --no-browser` on the host right before `cluster up`; the credentials are a snapshot and last 8 hours. An old CLI binary needs `AWS_SDK_LOAD_CONFIG=1`.
- **`cluster down` always with `-c <config file>`**, never with `--name` (that falls back to a `manager:master` image).
- **Search and replace only in named text files.** A tree-wide replace corrupted binaries in the round before.
- **Order that worked:** dev cluster with the prod build → new prod cluster next to the old one → compare answers of both → DNS switch → parallel days → delete the old one.
- **At the DNS switch**, in one step:
  1. two `update_route53.py` commands (API and dashboard record) with profile `production`

  5. move the two terraform stacks with EKS access entries to the new cluster name
